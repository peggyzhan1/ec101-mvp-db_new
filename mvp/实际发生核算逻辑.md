# 实际发生核算逻辑

核算函数是 `mvp/actual_result_calculator.py` 的 `calculate_actual_results`。它只读已经入库的一个 `import_batch_id`，不打开 `standard.xlsx`。

一次导入对应一次核算。快马和舟谱各有自己的导入批次、各自的活动行和券行，公式相同。活动编号、赠品名称、券名都来自库里的字段。

表和字段的存放位置见 [`EC101_标准库数据字典.md`](EC101_标准库数据字典.md)。两家数据怎么变成这些字段，见 [`快马数据转换与字段映射.md`](快马数据转换与字段映射.md) 和 [`舟谱数据转换与字段映射.md`](舟谱数据转换与字段映射.md)。

下文金额均保留两位小数。试点数字对应 2026-10-07 库里的当前批次：舟谱核算日 2026-09-23，快马核算日 2026-09-22。

## 1. 参与计算的字段

| 库表 | 字段 | 用来做什么 |
|---|---|---|
| activity | activity_id、activity_no、activity_type、promo_method、start_time、end_time | 遍历本批次活动；判断是不是赠品；没有核销时用开始、结束时间圈订单 |
| activity_benefit | benefit_type、gift_product_no、gift_product_name | `benefit_type='赠品'` 且编号或名称至少有一个非空，才得到赠品清单 |
| activity_execution | activity_id、order_id、discount_amount | 有核销行时，这些订单就是参加活动的订单。金额取 `discount_amount` |
| order_header | order_id、order_no、order_status、order_time | 释放判断；没有核销的满赠还用下单时间对活动窗口 |
| order_line | order_id、product_no、product_name、quantity | 赠品数量 = 命中行的 `quantity` 之和 |
| product | product_no、product_name | 订单行名称对不上时，再用同编号商品主数据的名称比对赠品名称 |
| coupon_redemption | status、discount_amount、order_id、coupon_no、customer_no、use_period | 只加总 `status='已使用'`。`order_id` 为空表示没有归到唯一订单 |
| coupon_config | coupon_config_id、coupon_name | 把已使用的券归到哪一份券汇总 |

导入时的列对应关系：

| 标准工作表列 | 库字段 |
|---|---|
| 标准活动核销明细.优惠金额 | activity_execution.discount_amount |
| 标准活动核销明细.订单号 | 先对上 order_header.order_no，再存 order_id |
| 标准活动权益.赠品商品编号 / 赠品商品名称 | activity_benefit.gift_product_no / gift_product_name |
| 标准活动.活动类型 / 促销方式 / 开始时间 / 结束时间 | activity.activity_type / promo_method / start_time / end_time |
| 标准订单明细.订单状态 / 下单时间 | order_header.order_status / order_time |
| 标准订单明细.商品编号 / 商品名称 / 数量 | order_line.product_no / product_name / quantity |
| 标准优惠券核销明细.状态 / 优惠金额 / 订单号 / 使用期限 / 客户编号 | coupon_redemption.status / discount_amount / order_id / use_period / customer_no |

## 2. 不参与本公式的字段

这些字段仍在库里，本核算不读取：

- `order_line.discount_amount`（订单行优惠金额）。舟谱这一列是优惠前金额减实付金额，快马这一列是源订单上的优惠金额。满减金额只来自 `activity_execution.discount_amount`。
- `activity_rule` 的门槛值、立减金额。
- `activity_scope`、`coupon_scope`，包括商品名称前缀、每客户次数、品牌、客户类型。
- `fulfillment` 的完成时间、出库时间、履约状态。完成时间为空时，释放判断继续看订单头。
- `coupon_redemption.status='已领取'` 的优惠金额。已领取不进发生额。客户未匹配的检查会看全部领用记录，包括已领取。

## 3. 核算日和释放线

```text
核算日 = 调用时传入的 calc_date，没有传则取运行当天的日期
释放线 = 核算日减 2 天，时间定为当天 00:00:00
```

舟谱试点传入 2026-09-23，释放线是 2026-09-21 00:00:00。快马试点传入 2026-09-22，释放线是 2026-09-20 00:00:00。费用平台页面上传时若不另传核算日，用的是上传当天。

只有日期、长度为 10 的时间文本，比较前会补时钟：当作开始边界时补 `00:00:00`，当作结束边界时补 `23:59:59`。已带时间的文本原样比较。

一张订单可释放，要同时满足：

```text
order_header.order_status = '已完成'
并且 order_time 非空
并且 补钟后的 order_time ≤ 释放线
```

订单状态不是「已完成」、下单时间为空，或下单时间晚于释放线，都不可释放。

## 4. 活动先走哪一条

对本批次每一条 `activity`：

```text
赠品清单 = 该活动下 benefit_type='赠品'，且赠品编号或赠品名称去掉空白后至少有一个不为空
文字像赠品 = activity_type 与 promo_method 拼在一起后含有「赠」
是赠品活动 = 赠品清单不为空，或文字像赠品
核销行 = 该活动的 activity_execution（order_id，discount_amount）
```

然后只进入下面一条：

| 条件 | 发生了什么 |
|---|---|
| 有核销行，并且是赠品活动 | 核销里的每张订单记一笔。优惠金额记 0。赠品数量取该订单上命中赠品的数量，不看活动开始结束时间 |
| 有核销行，并且不是赠品活动 | 核销里的每张订单记一笔。优惠金额 = 该行 `discount_amount`。赠品数量留空 |
| 没有核销行，是赠品活动，并且赠品清单不为空 | 在活动开始、结束时间之间，清点名称或编号命中的订单。每张订单记一笔，优惠金额记 0 |
| 没有核销行，文字像赠品，但赠品清单为空 | 不记发生笔数，记一条警告「赠品权益缺少赠品」 |
| 没有核销行，也不是赠品活动 | 不记发生笔数。汇总时仍写一行金额为 0 的活动费用 |

有核销的赠品若某张订单命中数量 ≤ 0，这张订单仍算一笔发生，数量为 0，并累计进警告「核销订单没有赠品行」。赠品清单为空、只是文字里带「赠」时，警告写成「赠品权益缺少赠品」。

## 5. 赠品数量怎么从字段加出来

赠品清单里的每一项都可以贡献匹配条件，各项之间是「或」：

```text
赠品名称不为空时：
  order_line.product_name = 赠品名称
  或 product.product_name = 赠品名称
赠品编号不为空时：
  order_line.product_no = 赠品编号
```

商品主数据按同一导入批次、同一商品编号左连接。因此行上的名称已经是赠品名称时，即使商品编号带 `UNMATCHED:` 也会命中。行上名称是空的、主数据名称等于赠品名称时也会命中。

同一订单命中多行时，`quantity` 相加，再保留两位小数。

没有核销行的那条路径会再加上时间条件。下单时间先按第 3 节补钟，再判断：

```text
补钟后的 order_time 介于 活动开始时间 与 活动结束时间 之间
```

活动开始若只有日期，补 `00:00:00`；结束若只有日期，补 `23:59:59`。有核销行的赠品不加这个时间条件，参加范围就是核销明细里的订单。

## 6. 优惠券怎么加

```text
已使用券 = coupon_redemption 中 status = '已使用'
券发生额 = 这些行的 discount_amount 之和
```

`order_id` 为空的已使用券照样进入发生额，不进入可释放额。

归到哪份券配置：

| 本批次券配置条数 | 归法 |
|---|---|
| 1 条 | 全部已使用券归到这一条 |
| 0 条 | 全部归到 `coupon_config_id` 为空的一份汇总 |
| 多条 | 配置名称非空，且名称是券号 `coupon_no` 的子串，并且这样的配置恰好一条，才归到它；否则归到空配置那一份 |

兴路强和羿柏当前各自只有一条券配置，因此该批次全部已使用券都归到这一条。

## 7. 写入的结果字段

### calculation_run

| 字段 | 算法 |
|---|---|
| calc_date | 核算日 |
| activity_benefit | 所有非赠品发生笔的优惠金额之和 |
| coupon_benefit | 全部已使用券的优惠金额之和，含未归到订单的券 |
| total_benefit | 上面两项相加 |
| status | `calculated` |

赠品发生笔的金额是 0，不增加 `activity_benefit`。

### entitlement_check

每一笔活动发生写一行。

| 字段 | 赠品发生笔 | 金额发生笔 |
|---|---|---|
| order_id / activity_id | 该订单、该活动 | 同左 |
| activity_benefit | 0 | 该笔 discount |
| coupon_benefit | 0 | 0 |
| total_benefit | 0 | 该笔 discount |
| gift_qty_entitled | 空 | 空 |
| gift_qty_actual | 该订单赠品数量 | 空 |
| consistency | 已发生 | 已发生 |

券不写 `entitlement_check`。券的发生和释放在 `coupon_fee_summary`。

### release_candidate

参加过活动发生笔的订单，以及已使用券能够对上的订单，每个 `order_id` 一行。

| 字段 | 值 |
|---|---|
| is_candidate | 满足第 3 节则为 1，否则 0 |
| reason | 可释放：「已完成且下单时间≤核算日减2天」；不可释放：「订单未完成或下单时间晚于核算日减2天」 |

### activity_fee_summary

每个活动一行。可释放子集 = 该活动发生笔里，订单满足第 3 节的那些笔。

赠品活动（发生笔标记为赠品，或没有任何发生笔但活动文字像赠品）：

| 字段 | 算法 |
|---|---|
| actual_discount_total | 0 |
| gift_cost_total | 0 |
| gift_qty_entitled | 空 |
| gift_qty_actual | 全部发生笔的赠品数量之和 |
| releasable_discount_total | 0 |
| releasable_gift_qty | 可释放发生笔的赠品数量之和 |
| release_order_count | 可释放发生笔的笔数 |
| settle_status | 按赠品数量统计(不结算单价) |

金额活动：

| 字段 | 算法 |
|---|---|
| actual_discount_total | 全部发生笔 discount 之和 |
| gift_cost_total | 0 |
| gift_qty_entitled / gift_qty_actual / releasable_gift_qty | 空 |
| releasable_discount_total | 可释放发生笔 discount 之和 |
| release_order_count | 可释放发生笔的笔数 |
| settle_status | 金额优惠 |

没有发生笔的金额活动，两个金额都是 0，可释放笔数是 0。

### coupon_fee_summary

每一份有券的配置写一行。空配置桶里若有券，再写一行 `coupon_config_id` 为空的汇总。

| 字段 | 算法 |
|---|---|
| used_count / used_amount | 桶内已使用券的张数、金额之和 |
| linked_amount | `order_id` 不为空的那些券的金额之和 |
| releasable_count / releasable_amount | 已对上订单、且该订单可释放的张数和金额 |
| unlinked_count / unlinked_amount | `order_id` 为空的张数和金额 |
| settle_status | 金额优惠 |

## 8. 质量问题

每次核算都会写一条提示「T-2释放口径」，原因里带上这次的释放线，并写明履约完成时间为空不否决释放。

另外三种按数据出现才写，级别都是警告：

| issue_type | 触发字段 |
|---|---|
| 核销订单没有赠品行 | 有核销的赠品活动里，命中数量 ≤ 0 的订单笔数 |
| 赠品权益缺少赠品 | 活动文字像赠品，但没有任何带名称或编号的赠品权益 |
| 返券双单号无法唯一归因 | 已使用、`order_id` 为空，且 `use_period` 以 `关联单据:` 开头并含逗号 |
| 返券单号未命中订单 | 其余已使用且 `order_id` 为空的券 |
| 券领取客户未匹配 | `customer_no` 非空，并且同一批次的 customer 里没有这个编号。已领取的券也计入张数 |

双单号和未命中订单的金额已经在 `coupon_benefit`、`used_amount` 里，不在 `releasable_amount` 里。

## 11. 费用页怎么读这些字段

当前模式取每个 `is_current=1` 批次最新的一次 `calculation_run`。活动行读 `activity_fee_summary`：金额类展示可释放金额，赠品类展示实际数量和可释放数量。券读 `coupon_fee_summary` 的可释放金额。赠品的结算状态是按数量统计，不进可提交金额。

两家当前批次放在一起时，可提交金额是各金额汇总的可释放额相加：快马满减 1995、快马测试券 200、舟谱返券 555，合计 2750。赠品实际数量是 111 + 98 = 209。
