# EC101 `_new` 后续实施计划

对照 Codex 对两个仓库的建议，以及本仓库（`ec101-mvp-db_new`）已经跑通的事实。目标是消迷雾：知道现在站在哪，下一步改什么、为什么改、先不改什么。

相关文档：[`快马转换与核算逻辑.md`](快马转换与核算逻辑.md)、[`标准数据到标准库对照.md`](标准数据到标准库对照.md)。

## 1. 两个项目各管什么

| 仓库 | 角色 | 怎么用 |
|---|---|---|
| [ec101-mvp-db](https://github.com/Zzh032811/ec101-mvp-db) | **业务正确性基准（Golden Reference）** | 冻结，不再开发。兴路强满减已对账数字是验收答案。 |
| 本仓库 `ec101-mvp-db_new` | **正式架构候选** | 只在这里改：平台转换器 → 标准数据 → 统一入库 → 核算 → 平台。 |

旧项目里兴路强满减的黄金答案（核算日 `2026-09-22`）：

| 指标 | 黄金答案 |
|---|---:|
| 活动订单 | 136 |
| 理论权益 | 2040 |
| 平台实际优惠 | 2040 |
| 一致订单 | 136/136 |
| T-2 可释放 | 133 |
| 可释放费用 | 1995 |
| 不可释放 | 3 |
| 不可释放金额 | 45 |

本仓库用真实快马文件已经对上：**活动订单 136、实际优惠 2040、可释放 133、可释放金额 1995、不可释放 3 / 45**。满赠单数 98/98、测试券 200 元也已经对上。

还没对上、也还没做的，是旧项目多出来的那一列：**用规则重算「理论权益」，再和平台实际比「一致/差异」**。当前 RESULT 的 `consistency` 固定写「按核销明细」，`activity_rule` 在快马自动转换里是空的。

## 2. Codex 说对了什么，哪一句不能照搬

### 该采纳

1. **冻结旧库，只改 `_new`，用旧数字当答案。** 本仓库已经在这么做。
2. **平台差异停在转换器。** `import_service` / 核算不得出现 `if 快马 / if 舟谱`。现在入库函数没有平台分支，必须保持。
3. **入库和核算拆开。** 现在 `import_snapshot` 写完业务表立刻 `calculate_batch`，两件事绑在一个函数里。以后要加理论重算、重跑核算、补血缘，不拆会越来越难查。
4. **一条链验完再扩。** 满减把「标准 → 入库 → 核算」钉死后，再扩满赠件数、券规则、舟谱。不要同时改契约和加平台。
5. **血缘要补。** 现在只有 `sources.zip` 的路径和哈希，标准行不知道来自哪个源文件、哪一行。费用闭环必须能从 RESULT 追到原始格子。
6. **三个验收问题。** 字段是通用事实还是某平台格式？换平台还成立吗？结果能不能追到业务事实再追到原始文件？

### 不能照搬的一句

Codex 的第一项开发任务写成：

> 把 Import 和 Calculation 拆开，并让新引擎**从规则重新计算理论权益，而不是直接 SUM 平台优惠金额**。

后半句会推翻已经确认、并且已经验过的口径：

- 费用只认核销明细里的优惠金额
- 不先做完整活动配置
- 满赠先按单数，不数赠品
- 券直接用「优惠金额」，测试券不排除

旧项目的 2040 其实是**两笔数碰巧相等**：规则算出理论 15×136，核销加总实际也是 15×136。本仓库目前只做了第二笔，所以 2040 / 1995 已经对上，但「理论权益」「一致 136/136」还没有单独算出来。

正确拆法：

| 数字 | 来源 | 用途 |
|---|---|---|
| 平台实际优惠 | 活动/券核销的优惠金额 | **计费、可释放金额**（已跑通，不要改成用规则代替） |
| 理论权益 | 活动规则（满 300 减 15 等） | **质量核对**：和实际比一致/差异 |
| 能否释放 | 订单状态 = 已完成，且下单时间早于核算日 T-2 | 已跑通 |

没有规则数据时，理论列为空，费用仍然按核销出。有规则之后，多一列核对，不改 1995。

标准契约里已经有「标准活动规则 / 权益 / 范围」，能表达「满 300 减 15」。缺的不是表，是快马转换没有把这条规则写进去（试点规则在配置截图里，不在活动明细 Excel 里）。

## 3. 现在已经完成、不必重做的

- 标准工作表清单（`mvp/standard_schema.py`）足以表达兴路强满减的**核销和订单事实**
- 快马转换器：源文件 → `standard.xlsx`（客户/商品/订单/按单聚合核销/政策文本取活动名）
- 统一导入：标准表 → 业务表；无平台 `if`
- 按核销 + T-2 的 RESULT，黄金答案中的实际侧已对齐
- 平台可看订单明细和费用
- 满赠单数、券金额已有回归测试（先冻结，不扩展）

不必再「从零发明 Standard」，也不必先做大数据库改版。

## 4. 实施顺序

只改 `_new`。每一步的出门条件都是：兴路强满减实际侧数字不变（136 / 2040 / 133 / 1995）。变了就沿着 Converter → Standard → CORE → Calculation 往回查，不先改表结构。

### 步骤 A — 把 Standard V1 冻成契约

**做什么：** 指定 `mvp/standard_schema.py` 为 **EC101 标准数据契约 V1**。本阶段不加字段。用文档写清：哪些表快马自动填、哪些表要手工/后续规则输入才有行（规则、权益、范围、券配置）。

**原因：** Codex 第一步是对的——后面所有平台都必须先翻译成这套数据。冻住是为了改转换器和核算时有固定靶子，不是再设计一套。

**出门条件：** 契约文件不再为「可能用到」加列；满赠/舟谱暴露缺口时再改，并写明改因。

### 步骤 B — 把入库和核算拆开（第一项开发任务）

**做什么：** 已落地为 `mvp/calculation_engine.py`。

```text
standard.xlsx
    → import_service     只校验、只写业务事实（CORE），状态 imported
    → calculation_engine 只读 CORE，只写 RESULT，状态 calculated
```

- `import_snapshot` 不再接收 `calc_date`，也不写 RESULT
- 上传接口仍自动调一次 `calculate_batch`（两个函数，不是混在导入里）
- 核算可对同一批次再跑一条 `calculation_run`，不重导 Excel
- 拆完后黄金答案数字必须与现在逐项相同
- 核算函数里不得出现平台名判断

**原因：** 这是 Codex 里唯一现在就该动代码、而又不改变业务口径的一步。不拆开，后面加理论核对、重跑、血缘都会和导入缠在一起，迷雾不会散。

**不做：** 这一步不要改计费公式，不要开始填活动规则，不要改前端交互。

### 步骤 C — 只盯兴路强满减，核对「标准 Excel 相对源文件」

**做什么：** 用试点源文件跑 `convert_kuaima`，在入库前抽查 `standard.xlsx`（建议固定 10 张活动订单 + 若干非活动订单）。核对：单据编号、客户、商品、数量、行金额、订单状态；核销是否按订单加总；不在活动明细里的单是否没有核销行。把抽查清单和结论写进测试或附录，能自动化的断言继续留在 `converters/tests` 和 `tests/e2e`。

**原因：** Codex「先验证 Converter，再入库」是对的定位方法。本仓库转换已有真实文件测试，缺的是可重复的抽查记录，不是再写一套转换器。

**若抽查失败：** 只改 `converters/kuaima.py` 或契约列语义，不改库表、不改核算。

### 步骤 D — 规则进标准表，理论权益只做核对、不计费

**做什么：**

1. 给兴路强满减补一条标准规则（门槛金额 300、立减 15）。来源是旧项目已经用过的配置截图/结构化输入，**不是**从活动明细猜。转换器已支持可选 `activity_inputs`。
2. 核算引擎增加：对有规则的活动算理论权益，和该单核销实际比「一致 / 差异」。
3. 可释放金额、结算草稿仍然用核销实际 + T-2。
4. 对账表补上旧项目的「理论 2040、一致 136/136」。这两格现在本仓库还是空的。

**原因：** 把旧 MVP / `mvp/scripts/promotion_calculator.py` 已验证的能力接回来，同时不推翻「费用以核销为准」。Codex 要的「从规则算理论」放在核对层，不放在计费层。

**若规则表仍为空：** 理论列为空，费用行为与现在完全相同。这样舟谱或未配规则的活动不会被卡住。

### 步骤 E — 标准行补来源标识

**做什么：** 每条写入的标准/CORE 事实至少能追到：`import_batch`、转换器版本、源文件、工作表、源行号或源业务键。不必把 RAW 整表再抄进 SQLite。`sources.zip` + 哈希保留。

**原因：** 没有这一步，RESULT → CORE → 原始格子这条证据链断在标准行。费用争议时只能打开整个 zip 手翻。Codex 把血缘单独列出来是对的，但放在拆分核算和满减理论核对之后做，避免和公式改动叠在一起。

### 步骤 F — 满赠（在满减对账表全绿之后）

**做什么：** 先保持现有「按单数、金额 0」。只有当步骤 D 的活动模型（规则 / 权益 / 范围）能表达「满 100、赠抱枕 ×1、不结算金额」时，再统计应赠/实赠件数。不能表达就改契约或权益表，仍然不改满减计费。

**原因：** 这是第一次测契约是否通用。提前数赠品会和「满减理论核对」抢同一套活动模型，问题分不清是规则引擎还是赠品口径。

### 步骤 G — 优惠券

**做什么：** 计费继续用券核销「优惠金额」（含测试券）。用真实数据看现有「活动域 / 券域分开、只在订单汇合」够不够表达配置、发放、使用、范围、核销。不够再补券域字段，不把券并回活动表来「讨论架构」。

**原因：** 两个项目的争议点正好在券。用数据证明模型，不要先争论券是不是 Activity。旧项目对券也没有做完整理论核算。

### 步骤 H — 舟谱

**做什么：** 只允许新增/改 `converters/zhoupu.py`。Standard、Import、Calculation、RESULT 尽量不动。若必须动 Standard，只能加**跨平台都成立**的履约概念（例如下游单号），不能加舟谱专属表。

**出门条件：** 除转换器外，CORE/核算无平台分支；旧快马黄金答案回归仍绿。

### 步骤 I — 这时才定物理模型 V1

表、外键、索引以 A–H 跑完后的实际读写为准，不再提前画「更专业」的库。

## 5. 第一项实际开发任务

**拆 `import_service` 与核算引擎，计费公式保持「SUM 核销 + T-2」。**

具体：

1. 把 `calculate_batch` / `run_calculation` / 释放规则迁到独立模块（例如 `mvp/calculation_engine.py`）。
2. `import_snapshot` 只负责校验和写入业务表。
3. API 上传成功后仍自动调一次核算，但调用关系是「导入结束 → 调引擎」，不是写在同一个事务职责里分不清。
4. 现有 e2e：满减 136 / 2040 / 133 / 1995、满赠 98/98、券 200，必须继续通过。

做完再进入步骤 C/D。不要把「恢复规则重算」和「拆函数」做在同一个变更里。

## 6. 明确先不做

- 不改旧仓库代码
- 不按「用规则代替核销」去改 1995
- 不在拆核算之前扩表、上舟谱、做赠品件数
- 不把 RAW 全量再导入一套并行库
- 不靠讨论把优惠券并进活动表

## 7. 每一步只问三个问题

1. 这个字段/表表达的是 EC101 通用事实，还是某个平台的导出格式？
2. 换一个平台，它还成立吗？
3. 从 RESULT 能否追到统一业务事实，再追到第三方原始证据？
