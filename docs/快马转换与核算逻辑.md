# 快马转换逻辑与 RESULT 核算逻辑

本文说明两件事：快马导出如何变成标准 Excel；导入后核算结果表（RESULT）怎么算费用。代码入口分别是 `converters/kuaima.py` 的 `convert_kuaima`，`mvp/import_service.py` 的 `import_snapshot`，和 `mvp/calculation_engine.py` 的 `calculate_batch`。标准表落到哪些库表，见 [`标准数据到标准库对照.md`](标准数据到标准库对照.md)。

当前只覆盖快马。舟谱转换器不在本文范围。

## 1. 整条链路

```text
快马源文件
  → 转换工具 convert_kuaima
  → standard.xlsx + sources.zip
  → import_snapshot 写入业务表（不核算）
  → calculate_batch 写出核算表（RESULT）
  → 平台读订单明细和费用
```

转换器**不写数据库、不算费用**。它只把平台列名改成固定标准表。费用全部在导入之后、按核销明细计算。

Windows 桌面工具 `desktop_converter/app.py` 和测试用的是同一套转换函数。界面角色对应源文件：

| 界面角色 | 转换器角色 | 试点目录里通常是 |
|---|---|---|
| 客户 | `customer` | `User-*.xlsx` |
| 商品 | `product` | `Product-*.xlsx` |
| 订单 | `order_detail` | `*-订单明细-*.xls` |
| 活动 | `activity_execution` | `*-活动明细-*.xls` |
| 优惠券 | `coupon_redemption` | `*-优惠券-*-活动明细-*.xls` |
| 履约 | `fulfillment` | 快马转换器**目前不读**这个角色 |

产出三个文件：`standard.xlsx`（标准数据）、`sources.zip`（源文件归档）、`conversion_report.txt`（行数和活动汇总）。导入清单里的「数据开始/结束日期」取自订单「下单时间」的最早、最晚一天。

## 2. 快马转换逻辑

处理顺序固定：客户 → 商品 → 订单 → 用订单行补商品 → 活动明细聚合成核销 → 自动生成活动主数据 → 优惠券核销 → 回填订单行上的活动/券号 → 用订单状态生成履约。

### 2.1 客户、商品：按列改名，一行还是一行

客户文件有「客户编号」才写入「标准客户」。商品文件有「商品编号」才写入「标准商品」。列对应如下（源列名 → 标准列名）：

| 源文件 | 源列 | 标准工作表 | 标准列 |
|---|---|---|---|
| 客户 | 客户编号 / 客户名称 / 客户类型 / 客户区域 / 详细地址 / 联系电话 / 添加时间 / 所属业务员 | 标准客户 | 同名 |
| 商品 | 商品编号 / 商品名称 | 标准商品 | 同名 |
| 商品 | 品牌 | 标准商品 | 商品品牌 |
| 商品 | 一级目录 | 标准商品 | 商品目录 |
| 商品 | 条形码 | 标准商品 | 商品条码 |
| 商品 | 规格值1 | 标准商品 | 商品规格 |
| 商品 | 单位 | 标准商品 | 基本单位 |
| 商品 | 换算关系1 | 标准商品 | 箱规，同时解析成「每箱基本单位数量」 |

订单里出现、商品主数据里没有的商品编号，会按订单行上的名称/目录/规格补一条最小「标准商品」，避免导入时因缺商品失败。

### 2.2 订单：每个商品行一条标准订单明细

源列「订单编号」变成「单据编号」。没有订单编号的行丢弃。同一订单多个商品行，标准表里仍是多行，不在这里合并。

| 源列 | 标准列 | 说明 |
|---|---|---|
| 订单编号 | 单据编号 | |
| 下单时间 | 下单时间 | 规范化成日期时间文本 |
| 客户编号 / 客户名称 | 同名 | |
| 商品编号 / 商品名称 / 商品目录 / 规格 / 商品条码 | 同名 | |
| 订货数量单位 | 单位 | |
| 订货数量 | 数量 | |
| 优惠前金额 | 优惠前金额 | |
| 优惠金额 | 优惠金额 | 平台订单行上的优惠，**核算不用** |
| 订货金额 | 实付金额 | |
| 订货单价 | 单价 | |
| 所属业务员 | 业务员 | |
| 订单来源 / 订单类型 / 订单状态 / 支付方式 | 同名 | 「订单状态」后面用来判断能否释放 |
| （空） | 活动编号、优惠券编号 | 先留空，后面用活动明细、券明细回填 |
| （空） | 下游订单编号、退货数量 | 快马导出没有，保持空 |

转换器内部用「每个单据编号第一次出现的那一行」记住订单头信息（客户、业务员、状态），后面活动核销要借客户编号。

### 2.3 活动明细：行级分摊加总成「一单一活动」

快马「活动明细」是**商品行**：同一订单、同一活动可以有多行，每行有一份「促销优惠金额」。费用口径要的是订单级，所以按 `(订单号, 活动编号)` 把「商品总金额」和「促销优惠金额」加总，写成「标准活动核销明细」一行。

活动名不来自单独的活动配置表，而来自「享受促销政策」整句。句子形如：

```text
参与[可口可乐满减]组合金额满¥300，立减¥15活动，为您节省¥1.24
```

用正则取出方括号里的名字，作为活动名称。取不到括号时，整句当作名称；名称仍为空则该行丢弃（计入 `unparsed_policy_rows`）。

活动编号默认等于活动名称（例如 `可口可乐满减`）。只有在转换时额外提供了手工活动配置、且「活动名称」对得上时，才改用配置里的「活动编号」。快马试点验收**没有**手工配置。

客户编号、客户、业务员优先从对应订单行取；订单文件里没有该单时，客户名称退回活动明细的「客户」列。

**不在活动明细里的订单，不会出现在标准活动核销明细里。** 后面核算也不会给这些订单记活动费用。

### 2.4 活动主数据：从核销里长出来

「标准活动」不是从配置截图来的。转换器先写入手工配置（若有），再对核销里出现过、但还没有主数据的活动补一行：

- 活动编号、活动名称：见上一节
- 活动类型：名称或政策文本里有「赠」→ `满赠`；否则有「减」→ `满减`；都没有 → `其他`
- 开始时间、结束时间、状态、叠加规则：空。导入允许这些字段为空

规则、权益、范围三张标准表，快马自动转换**不填**。它们不影响当前费用。

### 2.5 优惠券：平台「优惠金额」原样进核销

有「优惠券编号」才写入「标准优惠券核销明细」。

| 源列 | 标准列 |
|---|---|
| 优惠券编号 | 优惠券编号 |
| 客户编号 | 客户编号 |
| 领取人 | 客户 |
| 所属业务员 | 所属业务员 |
| 领取时间 / 使用时间 | 领取时间 / 使用时间 |
| 使用期限 | 使用期限 |
| 状态 | 状态 |
| 使用订单号 | 订单号 |
| 优惠金额 | 优惠金额 |

不按券名过滤。试点里的 `test1` 测试券照常转换、照常计费。券配置/发放/使用规则表同样只有手工输入才有行；快马自动转换不造规则。

### 2.6 订单行上的活动编号、优惠券编号：只展示

全部核销写完后，按订单号回填：

- 「活动编号」= 该单在活动核销里出现过的活动编号，去重后用 `;` 连接
- 「优惠券编号」= 该单在券核销里出现过的券号，同样连接

没参加活动的订单这两列为空。这两列进库后在 `order_line` 上，**核算函数不读它们**。订单行「优惠金额」也不参与核算。

### 2.7 履约：从订单状态抄一份

每个单据编号写一条「标准履约」：「履约订单状态」= 该单第一行的「订单状态」。出库时间、完成时间、结款状态为空。

即便桌面工具选了「履约」文件，`convert_kuaima` 目前也不读它。核算释放条件也**不读**履约表，只看订单头的状态和下单时间。

### 2.8 转换明确不算的事

- 不按满减门槛、赠品规则重算「应该优惠多少」
- 不核对销售明细、配置截图
- 不排除测试券
- 不把满赠拆成赠品件数
- 不写 SQLite

## 3. RESULT 核算逻辑

`import_snapshot` 只把标准表写入业务表，状态为 `imported`。核算由 `calculate_batch` 单独执行，写出 RESULT，并把批次状态改为 `calculated`。平台上传仍是「导入成功后自动调一次核算」。核算日 `calc_date` 为 `YYYY-MM-DD`；上传时可指定，缺省为当天。兴路强验收固定为 `2026-09-22`。

RESULT 指这五张表，都不来自 Excel：

| 表 | 一行是什么 |
|---|---|
| `calculation_run` | 这一批导入的一次核算汇总 |
| `entitlement_check` | 每张**参与订单**的活动优惠 + 券优惠 |
| `release_candidate` | 同一张参与订单是否可释放、原因 |
| `activity_fee_summary` | 每个活动的参与/可释放/待释放单数和金额 |
| `calculation_quality_issue` | 不可释放的参与订单（类型「未达释放节点」，级别「提示」） |

### 3.1 费用只来自两张核销表

| 金额 | 取法 |
|---|---|
| 活动优惠合计 `activity_benefit` | 本批次全部 `activity_execution.discount_amount` 之和 |
| 券优惠合计 `coupon_benefit` | 本批次全部 `coupon_redemption.discount_amount` 之和 |
| 合计 `total_benefit` | 上面两项相加 |

不读 `order_line.discount_amount`，不读订单行上的活动编号/券号，不读活动规则/权益，不读履约表。满赠核销的优惠金额是 0，所以活动优惠合计可以是 0，但单数仍会统计。

### 3.2 哪些订单算「参与」

同时满足：属于本导入批次，**并且**至少有一条活动核销 **或** 一条券核销（券必须已经匹配到 `order_id`）。

没有核销的订单可以出现在业务数据页，但不会进入 `entitlement_check` / `release_candidate`，也不计入参与单数、可释放单数。

每张参与订单：

- 活动优惠 = 该单所有活动核销优惠之和
- 券优惠 = 该单所有券核销优惠之和
- `consistency` 固定写成「按核销明细」（不再用规则重算理论值去比对）

### 3.3 能否释放：已完成，且下单时间早于核算日前 2 天 0 点

```text
释放截止时刻 = 核算日 00:00:00 减去 2 天
可释放      = 订单状态恰好是「已完成」
             且 下单时间非空
             且 下单时间 < 释放截止时刻
```

核算日 `2026-09-22` 时，截止时刻是 `2026-09-20 00:00:00`。`2026-09-19 23:59:59` 的已完成订单可释放；`2026-09-20 00:00:00` 及更晚的不可释放。

| 条件 | `is_candidate` | 原因 |
|---|---|---|
| 状态不是「已完成」 | 0 | `订单状态=部分发货`（或实际状态原文） |
| 下单时间为空 | 0 | `下单时间缺失` |
| 下单时间 ≥ 截止时刻 | 0 | `未达T-2(下单 …)` |
| 其余 | 1 | `已完成且达到T-2` |

不可释放的参与订单再写一条质量问题，级别是「提示」，不阻断导入。

可释放活动金额、可释放券金额，只把 `is_candidate=1` 的订单上对应优惠加起来。`calculation_run.participating_orders` 是参与订单数；`released_orders` 是其中可释放的单数。

### 3.4 按活动汇总

每个活动看它的核销行，再和该单的 `release_candidate` 对齐：

| 字段 | 含义 |
|---|---|
| `actual_discount_total` | 该活动核销优惠合计（满赠为 0） |
| `gift_cost_total` | 固定 0（赠品件数未做） |
| `participating_orders` | 该活动核销单数 |
| `released_orders` / `released_amount` | 其中可释放的单数 / 金额 |
| `pending_orders` / `pending_amount` | 参与 − 可释放 |

一张订单既有满减又有券：活动汇总只含活动核销金额；券金额只在 `calculation_run` 和该单的 `release_candidate` 里。

### 3.5 核算明确不做的事

- 不用「满 300 减 15」去验平台优惠对不对
- 不统计满赠应赠/实赠件数
- 不把赠品折成人民币
- 不按 TPM 预算卡上限
- 不读履约表决定释放

## 4. 用兴路强试点把两段逻辑串起来

数据在 `快马-兴路强-试点/`。核算日 `2026-09-22`，截止 `2026-09-20 00:00:00`。基线是旧库 `mvp/ec101_mvp.db` 已对账数字。

### 满减 + 测试券

源文件：客户、商品、`满减/*订单明细*`、`满减/*活动明细*`、`优惠券/*活动明细*`。

转换后：

1. 活动政策句里取出「可口可乐满减」，类型「满减」
2. 活动明细按订单加总，得到 **136** 条标准活动核销，每单优惠 **15**，合计 **2040**
3. 券明细 1 条，优惠 **200**，不因名字叫 test1 而丢掉
4. 不在这 136 单里的订单，标准核销里没有它们，核算也不给活动费

核算后：

| 指标 | 数 |
|---|---|
| 活动优惠合计 | 2040 |
| 券优惠合计 | 200 |
| 参与订单 | 136（测试券用在其中一单上，不另加一张参与订单） |
| 可释放订单 | 133 |
| 可释放活动金额 | 1995（133×15） |
| 待释放 | 3 单、45 元，原因均为「订单状态=部分发货」 |

订单行上的优惠可以和核销不一致。例如单据 `1012420526026091000081` 行优惠合计 215 = 满减 15 + 券 200；计费仍只取核销里的 15 和 200。

### 满赠

源文件：客户、商品、`满赠/*订单明细*`、`满赠/*活动明细*`。政策句里有「赠」，活动类型「满赠」。核销优惠为 0，所以活动金额是 0；参与/可释放均为 **98** 单。

## 5. 怎么证明这两段是对的

不是看有没有 `standard.xlsx`，而是转换 + 导入 + 核算后的数字必须等于上一节的基线。

| 测什么 | 测试 |
|---|---|
| 政策取名、行级加总、订单行回填、真实满减文件 136 单 / 2040 元 | `converters/tests/test_kuaima_converter.py` |
| 桌面工具同一入口跑真实文件，核算对齐旧 MVP；业务数据接口和费用接口读同一套数 | `tests/e2e/test_standard_pipeline.py` |
| 释放规则（已完成、T-2、无核销不计） | `mvp/tests/test_import_service.py` |

重新跑：

```bash
python3 -m unittest converters.tests.test_kuaima_converter tests.e2e.test_standard_pipeline mvp.tests.test_import_service
```

对照旧项目之后要改什么（入库与核算拆开、理论权益只做核对），见 [`后续实施计划.md`](后续实施计划.md)。
