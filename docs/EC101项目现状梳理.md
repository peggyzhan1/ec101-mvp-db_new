---

## 1. 一句话定位

EC101 促销费用数据底座 + 费用运营台：把快马 / 舟谱等平台导出数据，统一成标准 Excel，写入 SQLite，按「核销明细 + 订单已完成 + T-2」核算可释放费用，再在费用运营台只读展示。

---

## 2. 主链路（现行唯一路径）

```text
平台源文件（快马 / 舟谱）
  → converters / desktop_converter（Windows 桌面工具）
  → standard.xlsx + sources.zip
  → POST /api/imports（校验并写入 CORE 业务事实）
  → calculation_engine.calculate_batch（写入 RESULT）
  → ec101-fee-platform-v1 只读展示
```

### 本地启动

```bash
python3 api/server.py
cd ec101-fee-platform-v1
npm run dev
```

默认 API：`http://127.0.0.1:8787`。前端开发服务器会把同源 `/api` 转发到该地址。

Windows 业务侧：运行 `desktop_converter/app.py`（或打包后的 `EC101StandardConverter.exe`），生成标准工作簿后再在费用台「数据接入」页上传。

## 4. 数据库

### 4.1 两套物理库（不要混用）

| 库文件 | DDL | 角色 |
|---|---|---|
| **`mvp/ec101_standard.db`** | `mvp/ddl/ec101_standard_sqlite.sql` | **费用平台现行库** |
| `mvp/ec101_mvp.db` | `mvp/ddl/ec101_mvp_sqlite.sql` | 历史样例 / 黄金参考；不自动迁移 |

- 无 Postgres / MySQL；当前全是 SQLite。
- `ec101_standard.db` 在 `.gitignore` 中；克隆后需重建或使用 `docs/samples/` 下的验收快照。
- 字段权威说明：[`mvp/EC101_标准库数据字典.md`](../mvp/EC101_标准库数据字典.md)。
- 旧库说明：[`mvp/EC101_MVP数据库使用说明V1.md`](../mvp/EC101_MVP数据库使用说明V1.md)（仅历史参考）。

### 4.2 标准库分层（25 表）

| 层 | 表 | 一行代表什么 |
|---|---|---|
| 导入 | `import_batch`、`import_file`、`import_validation_issue` | 一次标准工作簿上传及归档 |
| 主数据 | `dealer_platform`、`customer`、`product` | 经销商平台、客户、商品 |
| 订单 | `order_header`、`order_line`、`fulfillment` | 订单头、订单行、履约 |
| 活动 | `activity`、`activity_rule`、`activity_benefit`、`activity_scope`、`activity_execution` | 活动配置与已核销订单 |
| 优惠券 | `coupon_config`、`coupon_issue_rule`、`coupon_use_rule`、`coupon_scope`、`coupon_redemption` | 券配置与领用 / 核销 |
| 核算 | `calculation_run`、`entitlement_check`、`release_candidate`、`activity_fee_summary`、`coupon_fee_summary`、`calculation_quality_issue` | 一次核算及其明细 / 汇总 |

要点：

- 客户、商品、订单、活动、券均带 `import_batch_id`。
- 同一经销商 + 平台 + 覆盖区间再次导入时，旧批次 `is_current=0`，新批次 `is_current=1`；旧行保留。
- 费用页「当前」模式只读 `is_current=1` 批次，且每个批次取最新一次 `calculation_run`。
- 活动和优惠券是独立域，只通过订单间接汇合；费用在 RESULT 分别汇总。
- 新 DDL **不再**创建 `raw_*`、`std_*`、`tpm_*`；原始文件只作为 `sources.zip` 归档（路径、哈希、大小）。

### 4.3 标准工作簿 → 库表

| 工作表 | 写入的表 |
|---|---|
| 导入清单 | `import_batch` |
| 标准客户 | `customer` |
| 标准商品 | `product` |
| 标准订单明细 | `order_header`、`order_line` |
| 标准活动 / 规则 / 权益 / 范围 / 核销明细 | `activity*` |
| 标准优惠券配置 / 发放 / 使用 / 范围 / 核销明细 | `coupon_*` |
| 标准履约 | `fulfillment` |
| sources.zip | `import_file` |

核算表不来自工作簿，由核算引擎在导入后写入。

### 前端导航

- **数据底座**：数据接入、主数据与映射、数据质量、业务数据
- **费用与促销 TPM**：运营总览、活动中心、权益核算、ROI 分析、证据与异常、核销与对账、结算批次

### 核算口径（已确认）

| 数字 | 来源 | 用途 |
|---|---|---|
| 平台实际优惠 | 活动 / 券核销明细的优惠金额 | **计费、可释放金额** |
| 理论权益 | 活动规则（如满 300 减 15） | **质量核对**（一致 / 差异），不计费 |
| 能否释放 | 订单状态 = 已完成，且下单时间早于核算日 T-2 的 00:00:00 | 释放候选 |

满赠按单数 / 件数统计，不折算单价结算。券用核销「优惠金额」（含测试券）。

## 8. 技术栈

| 层 | 技术 |
|---|---|
| 后端 | Python 3.9+，标准库 `http.server`（无 FastAPI / Flask） |
| 数据库 | SQLite（`PRAGMA foreign_keys=ON`） |
| 转换 | Python；桌面端 Tkinter + PyInstaller |
| 前端 | React 19 + vinext/Vite + Tailwind；Node ≥ 22.13 |
| 测试 | pytest（api / mvp / converters）、vitest（前端）、`tests/e2e` |

关键代码入口：

- `mvp/standard_schema.py` — 标准 Excel 契约
- `mvp/import_service.py` — 入库（不写 RESULT）
- `mvp/calculation_engine.py` — 核算（API 主用）
- `api/server.py` — 查询与导入服务
- `ec101-fee-platform-v1/app/page.tsx` — 运营台界面

## 9. 易混淆点（合并后常见误判）

1. **双库**：`ec101_mvp.db`（旧四层）≠ `ec101_standard.db`（现行）；表名不可混查。
2. **双核算入口**：API 实际调用 `calculation_engine.calculate_batch`；`actual_result_calculator` 是并行脚本路径，文档表述可能不一致。
3. **舟谱转换双路径**：`zhoupu_snapshot.py`（费用台已用、含 XD 逻辑）vs `zhoupu.py` / 桌面通用直译（能力更弱）。
4. **旧脚本仍在仓库**：ingest、早期 promotion 样例不影响主链路，但搜索时会干扰判断。
5. **「满减」语义**：舟谱试点「满减」文件夹实际是返券；兴路强才是金额满减。
6. **DDL 与实库漂移**：`calculation_run` 等表可能与最新 DDL 不完全一致；以实库观察数据，以 DDL 对齐目标。
7. **远程残留分支**：以 `origin/main` 为现行真相；历史 feature 分支仅作履历。

## 10. 现在站在哪、下一步做什么

### 已完成（不必重做）

- 标准工作表契约足以表达兴路强满减核销与订单事实
- 快马转换 → 统一导入 → 按核销 + T-2 的 RESULT，黄金答案实际侧已对齐
- 满赠单数、券金额有回归；理论核对已接到规则层
- 舟谱进标准库并可在费用台与快马一并展示
- ROI、数据字典、核验报告样例已落地

### 后续优先（详见 [`后续实施计划.md`](后续实施计划.md)）

1. **血缘**：标准行追到源文件 / 工作表 / 行号（不只 `sources.zip` 哈希）
2. **契约冻结**：缺口再改字段，不为「可能用到」扩列
3. **生产化**：受管数据库 + 认证权限 + 审计
4. **闭环能力**：异常确认、负责人、结算 / ERP 上账
5. **核验报告模版评审**后正式启用

### 明确先不做

- 不改旧仓库代码
- 不用「规则代替核销」去改 1995 等已确认费用数字
- 不把 RAW 全量再导入一套并行库
- 不靠讨论把优惠券并进活动表
